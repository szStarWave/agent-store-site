# 架构设计与系统规范

Flowy Agent Store 采用**本地优先（Local-First）**、高度解耦且基于事件溯源（Event Sourcing）的系统架构。云端服务仅负责资源定义的分发与检索索引，本机的宿主运行时全权接管模型推理调度、工具沙箱调用、工作区状态持久化与敏感凭据托管。

---

## 1. 系统分层拓扑

系统自上而下划分为资产分发层、摄取与目录层、运行时适配层、执行引擎内核、协议通讯层及客户端表现层：

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                    云端与分发层 (Distribution Layer)                     │
│  ModelScope 官方归档 (ZIP) │ Git / GitHub 仓库 │ 本地清单目录 (Directory)  │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ SHA-256 校验 / 规范化解析
┌────────────────────────────────────▼────────────────────────────────────┐
│                    资产摄取与目录层 (Ingestion & Catalog)                 │
│  Importer 导入引擎 ───► PluginSnapshot (不可变快照) ───► 本地 Catalog 索引 │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ 领域模型解耦
┌────────────────────────────────────▼────────────────────────────────────┐
│                 运行时适配与编排层 (Runtime Adapter & Team)               │
│  Agent / Skill / Connector 模型适配 ───► Agent Team (Planned DAG 引擎)   │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ 内部执行指令映射
┌────────────────────────────────────▼────────────────────────────────────┐
│                    执行引擎内核 (allo Execution Engine)                  │
│  Rust 异步运行时 (Tokio) │ 工具沙箱 │ MCP 协议宿主 │ 事件总线 (Event Bus) │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ App Server Protocol (JSON-RPC 2.0)
┌────────────────────────────────────▼────────────────────────────────────┐
│                  网络通讯与接入层 (Wire Protocol Layer)                   │
│  WebSocket 双向实时流 (Events / Control) │ HTTP 管理端点 │ 端口互斥锁     │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ 跨平台客户端抽象
┌────────────────────────────────────▼────────────────────────────────────┐
│                    应用表现层 (Presentation Layer)                       │
│     Flowy 内嵌 Web UI      │      TypeScript SDK     │     Flowy CLI    │
└─────────────────────────────────────────────────────────────────────────┘
```

各层级具有严格的职责划分与依赖单向性：

| 架构层级 | 核心组件 | 职责边界 | 状态与生命周期特性 |
| --- | --- | --- | --- |
| 资产分发层 | ModelScope CDN、Git 远程源、文件清单索引 | 维护专家、技能、连接器的元数据包及版本归档 | 无状态，远程只读，内容基于 SHA-256 内容摘要寻址 |
| 资产摄取层 | Importer 导入引擎、PluginSnapshot 快照系统、Catalog 索引 | 路径校验、逃逸防御、元数据解析、生成不可变快照及本地登记 | 快照写入后完全只读不可变，版本变更生成新快照实例 |
| 编排与适配层 | Runtime Adapter 适配器、Agent Team 编排器、DAG 调度器 | 领域对象映射、规划上下文动态派生、步骤拓扑依赖解析与并发控制 | 运行时动态求值，会话隔离，成员私有 Prompt 物理隔离 |
| 执行引擎内核 | `allo` 原生核心（Rust 实现）、异步调度器、MCP Client 宿主 | 单二进制进程、模型 API 通讯、沙箱工具调度、单向事件日志落地 | 守护进程级常驻，基于 SQLite WAL 与本地工作区持久化 |
| 协议接入层 | App Server 协议引擎、WebSocket 服务端、认证网关 | JSON-RPC 2.0 序列化、协议版本握手校验、连接鉴权、不透明 ID 转换 | 有状态长连接，支持重连增量重放与游标追平 |
| 应用表现层 | 内嵌 React 工作台（Web UI）、TypeScript SDK、CLI 初始化工具 | 用户交互界面呈现、流式渲染、命令调用与本地凭据配置辅助 | 客户端生命周期，与底层执行引擎通过标准协议解耦 |

## 2. 核心子系统架构

### 2.1 allo 原生执行引擎（Rust Core）

系统核心运行时 `allo` 完全采用 Rust 语言构建，并打包为独立的单可执行二进制文件进行分发：

- **零外部运行时依赖**：宿主机无需预装 Node.js、Python、Docker 或任何系统级动态链接库，解压即运行；
- **轻量异步并发**：基于 Tokio 异步运行时，单线程即可支撑数百个并发会话的事件调度，内存占用显著低于同类基于 Electron 或 Python 的方案；
- **进程级崩溃隔离**：模型推理网络调用、长时间运行的批处理任务及外部工具调用均运行在受控的异步协程内，单一任务超时或异常不会导致宿主进程崩溃；
- **确定性执行调度**：所有运行时副作用（文件写入、网络请求、环境变量读取）均经由统一的 I/O 栅栏进行审计与事件记录。

### 2.2 App Server 协议层

应用层（Web UI、TypeScript SDK、CLI）与 `allo` 核心运行时之间通过标准的 **App Server 协议** 进行交互：

- **通讯载体**：采用双向 WebSocket 长连接传输主干数据流（会话生命周期、实时 Token 流、工具调用确认、DAG 步骤流转），辅以 HTTP 协议处理二进制上传、健康检查与连通性探针；
- **JSON-RPC 2.0 规范**：全量控制指令（如 `conversation/create`、`conversation/send`、`run/cancel`）均遵循 JSON-RPC 2.0 规范，提供严格的请求响应匹配与强类型错误码；
- **不透明资源标识（Opaque Identifiers）**：所有对客户端公开的实体 ID（例如 `conv_...`、`run_...`、`snap_...`）均为混淆后的不透明字符串，严格屏蔽底层数据库自增主键与宿主机文件物理路径；
- **协议版本指纹握手**：宿主进程启动成功后，向 stdout 打印单行包含协议指纹与鉴权模式的 JSON 通知，客户端建连时必须核对 `protocol_version` 是否全等：

```json
{"agent_store":"listening","host":"127.0.0.1","port":8787,"url":"http://127.0.0.1:8787/","protocol_version":"fp-12","version":"0.8.2","auth":"disabled-local"}
```

### 2.3 资产摄取与不可变快照系统

外部插件或市场资产进入本地运行时必须经过严苛的摄取管线（Importer Pipeline），杜绝恶意代码逃逸与依赖版本漂移：

```text
[ 外部市场源 / 插件目录 / 本地目录 ]
                 │
                 ▼
1. 来源定位与 Manifest 解析 (plugin.json / marketplace.json / connectors.json)
                 │
                 ▼
2. 静态安全检查 (路径穿越 ../ 检测、符号链接 Symlink 逃逸阻断、文件权限审查)
                 │
                 ▼
3. 计算全树 SHA-256 内容摘要 (content_digest)
                 │
                 ▼
4. 复制至版本化归档目录 (~/.agent-store/snapshots/<slug>-<digest>/)
                 │
                 ▼
5. 生成 PluginSnapshot (记录版本清单、依赖关系、兼容性评估矩阵)
                 │
                 ▼
[ 写入本地 SQLite Catalog 资源目录，供运行时安全加载 ]
```

- **快照不可变性**：快照一旦写入文件系统并登记数据库，即设为只读。任何源码修改或上游更新均触发生成全新的快照实体；
- **执行版本锁定**：运行中（In-Flight）的会话与 Run 严格绑定其启动时刻的 `PluginSnapshot` 实例，不受宿主后台进行资产更新或 Catalog 变动的影响；
- 详细的插件规范与市场协议见 [插件与市场](/zh-CN/docs/plugins-market)。

### 2.4 本地存储与并发隔离机制

系统遵循本地数据主权原则，所有业务状态、会话记录与资产缓存均持久化于本地受控数据目录（`--data-dir`）：

```text
~/.agent-store/ (或平台用户目录，如 %LOCALAPPDATA%\Flowy\Nomi-dev)
├── config.toml               # 宿主全局配置文件 (API 供应商 / 默认市场 / 代理)
├── mcp.json                  # 本机静态私有 MCP Server 声明
├── store.db                  # SQLite 核心数据库 (WAL 模式，存储会话、Runs、Catalog)
├── store.db-wal              # SQLite 预写式日志
├── store.lock                # 宿主单实例互斥文件锁 (Single-Instance Mutex)
├── snapshots/                # 不可变资产快照物理归档
│   └── <slug>-<digest>/      # 单个快照解包目录 (技能脚本 / 提示词 / 静态资源)
└── workspaces/               # Agent 执行工作空间
    └── <workspace_id>/       # 运行时沙箱目录 (中间临时产物 / 生成文档)
```

- **单实例互斥锁**：通过操作系统级文件排他锁（`store.lock`）确保同一数据目录在同一时刻仅能被一个 `flowy-agent-store` 进程打开，防止多进程并发写入导致 SQLite 损坏；
- **WAL 并发模式**：SQLite 数据库默认启用 WAL（Write-Ahead Logging）模式，读取请求与写入请求互不阻塞，保障高频流式事件写入时前端界面的流畅查询。

### 2.5 凭据机要区与安全边界

系统采用「凭据零泄露」与「最小知识原则（PoLP）」设计敏感认证信息的管理机制：

- **`secret:<KEY>` 模式抽象**：连接器配置中不直接存储明文 Token 或 API 密钥，仅持有命名凭据引用；
- **本地凭据隔离金库**：实际明文凭据加密存储于本地受操作系统保护的安全存储（如 Keychain / DPAPI / 受限文件权限凭据库）中；
- **接口脱敏**：App Server 协议与 Web UI 仅能获取凭据的配置状态（`configured: true`）、关联账号遮罩（如 `ak-****98a`）及过期时间，明文凭据禁止经由 WebSocket 或 HTTP 响应返回；
- **网络访问边界**：系统默认以 `127.0.0.1` 本地免密可信模式启动；当监听公开网卡时（如 `--host 0.0.0.0`），强制要求启用 `--auth` 密码鉴权网关；
- 详细的配置项与命令行参数详见 [配置文件](/zh-CN/docs/configuration) 与 [命令行用法](/zh-CN/docs/cli)。

## 3. Agent 运行时与编排模型

### 3.1 单 Agent 执行生命周期

单个 Agent 在会话中的执行由确定性有限状态机驱动，贯穿上下文组装、模型推理、工具调度与事件反馈：

```text
[ 用户提交 Prompt ]
         │
         ▼
┌─────────────────┐
│ ContextAssembly │ ◄── 组装：系统 Prompt + Agent Preset + 绑定的技能/连接器 Schema + 历史窗口
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ ModelInference  │ ◄── 流式接收 LLM 输出，解析思考过程与工具调用声明 (Tool Calls)
└────────┬────────┘
         │
    ┌────┴───────────────────────────┐
    ▼                                ▼
[ 产出文本 Token ]             [ 触发工具调用 ]
    │                                │
    │                                ▼
    │                     ┌────────────────────┐
    │                     │ PermissionBarrier  │ ◄── 校验工具权限与沙箱路径
    │                     └──────────┬─────────┘
    │                                │ (通过)
    │                                ▼
    │                     ┌────────────────────┐
    │                     │ ToolExecutionHost  │ ◄── 本地协程执行 / MCP Server 调度
    │                     └──────────┬─────────┘
    │                                │
    │                                ▼
    │                     [ 工具输出回填上下文 ] ───────┐
    │                                                  │
    └──────────────────────────────────────────────────┘
         │
         ▼ (无后续工具调用)
┌─────────────────┐
│ RunCompleted    │ ──► 写入终态事件，持久化生成产物 (Artifacts)，通知客户端
└─────────────────┘
```

### 3.2 Agent Team（V1）计划有向无环图编排

针对复杂多步骤任务，Flowy Agent Store 引入了固定成员名册与 Leader 规划驱动的 **计划有向无环图（Planned DAG）** 编排引擎：

```text
[ 用户复杂任务需求 ]
         │
         ▼
┌────────────────────────────────────────┐
│ Leader Agent 规划阶段 (Planning Context) │ ◄── 动态派生规划上下文，不污染常规会话
└──────────────────┬─────────────────────┘
                   │
                   ▼ 生成初始执行图 (Planned DAG)
      ┌─────────────────────────┐
      │  Step 1: 市场数据抓取    │ ─── (Agent A: 爬虫专家)
      └────────────┬────────────┘
                   │
         ┌─────────┴─────────┐
         ▼                   ▼ (并行并发执行)
┌─────────────────┐ ┌─────────────────┐
│ Step 2: 竞品分析 │ │ Step 3: 定价建模 │ ─── (Agent B: 分析师 / Agent C: 财务专家)
└────────┬────────┘ └────────┬────────┘
         └─────────┬─────────┘
                   ▼ (依赖汇聚)
┌────────────────────────────────────────┐
│ Leader 评估节点 (Evaluation & Replan)  │ ◄── 检查产物质量，评估分支可行性
└──────────────────┬─────────────────────┘
                   ├───────────────────────┐ (产物不满足预期)
                   ▼ (顺利通过)             ▼
┌──────────────────────────────────┐ ┌──────────────────────────────────┐
│ Step 4: 整合交付报告 (Agent D)    │ │ 动态重规划 (Dynamic Re-planning) │
└──────────────────┬───────────────┘ └─────────────────┬────────────────┘
                   │                                   │ 动态修补剩余 DAG 拓扑
                   ▼                                   └───────────────► 重新调度
[ 任务流转终态：Succeeded ]
```

- **Leader 规划角色约束**：Leader 专注于全局目标拆解与执行图拓扑维护。Leader 不创建独立对话历史，其规划 Prompt 在执行前动态合成，与团队成员的私有指令物理隔离；
- **步骤细粒度并发与重试**：无拓扑依赖的步骤（如上图 Step 2 与 Step 3）由调度引擎并发派发给对应专家处理；单步骤执行失败触发局部重试策略，避免整图回滚；
- **动态重规划（Dynamic Re-planning）**：中间步骤如果暴露出信息缺失或逻辑矛盾，评估节点可触发 Replan 协议，由 Leader 在保留已完成步骤产物的前提下，动态调整后续待执行子图；
- **人工干预闭环（Human-in-the-Loop）**：关键决策节点可暂停图流转，进入等待决策状态，通过 SDK 的 [`client.runs.answer`](/zh-CN/docs/typescript-sdk) 注入外部用户仲裁结果。

| 架构维度 | 单 Agent 会话模式 | Agent Team（V1）DAG 编排模式 | 核心设计约束 |
| --- | --- | --- | --- |
| 规划形态 | 单轮/多轮反应式（Reactive）Prompt 响应 | 先规划（Planned）、后执行、动态重修图拓扑 | 严禁无图乱序执行，所有步骤执行前必须存在确定性节点 |
| 上下文隔离 | 全量上下文堆叠在同一 Session 窗口中 | 步骤上下文独立切片，成员间仅通过明确产物交付物交互 | 成员私密系统指令物理隔离，防止提示词交叉污染 |
| 并发能力 | 串行执行（单一模型思考流） | 拓扑无关节点原生并行调度 | 严格按 DAG 依赖栅栏同步状态，杜绝数据竞争 |
| 干预机制 | 用户在下一轮对话输入文本补充指导 | 结构化问答决断（`run/answer`）与中断恢复 | 外部决断结果作为确定性输入持久化进事件图谱 |

## 4. 事件驱动架构与状态投影

### 4.1 追加写入事件日志（Single Source of Truth）

系统全面拥抱 **CQRS（命令查询职责分离）** 与 **事件溯源（Event Sourcing）** 理念：

- **事件日志为唯一真源**：执行过程中的所有动作（状态流转、模型输出 Token、工具调用发起、工具返回、文件写入、错误抛出）均以不可篡改的单向事件追加写入本地数据库；
- **状态视图即投影（Projection）**：用户看到的会话列表、Run 执行状态、DAG 节点进度图、生成的文件资产等，均为底层事件流在特定维度的内存或数据库查询投影；
- **确定性历史回放**：任何历史 Run 均可通过自首个事件起顺序回放，完全还原当时的推理路径与执行现场。

| 事件类别 | 代表性 Event Type | 载荷核心字段 | 派生投影目标 |
| --- | --- | --- | --- |
| 生命周期事件 | `run/created`, `run/completed`, `run/failed` | `run_id`, `status`, `timestamp`, `error_code` | Run 终态标记、耗时统计、计费计量 |
| 规划编排事件 | `team/dag_planned`, `team/step_started`, `team/replan` | `nodes`, `dependencies`, `step_id`, `diff` | DAG 拓扑图渲染、步骤进度百分比、活跃节点高亮 |
| 推理交互事件 | `message/delta`, `reasoning/delta` | `message_id`, `role`, `content`, `delta` | 前端流式打字机效果、思维链面板折叠展示 |
| 工具集成事件 | `tool/called`, `tool/completed`, `tool/failed` | `call_id`, `tool_name`, `arguments`, `output` | 工具调用展开面板、外部系统同步状态、审计追踪 |

### 4.2 流式传输与可靠追平机制

为在弱网、页面刷新或客户端重启场景下提供坚韧的用户体验，事件流引入了单调自增序号与游标恢复机制：

```json
{
  "sequence": 1042,
  "run_id": "run_01j7x8a9bcdef0123456789abc",
  "event_type": "team/step_completed",
  "timestamp": 1774780800000,
  "payload": {
    "step_id": "step_extract_data",
    "status": "succeeded",
    "artifact_id": "art_01j7x8b0123456789abcdef012"
  }
}
```

- **单调自增 `sequence`**：同一 Run 内生成的所有事件具备全局连续的序号，客户端通过检测序号连续性即时感知丢帧；
- **增量重放游标（Cursor Replay）**：客户端重连时发起携带参数的订阅请求（如 `run/events?after=1041`），服务端仅推送断连期间积压的差异事件，避免全量重查造成性能开销；
- **会话状态全量补全**：若客户端断线时间过长超出内存滑动窗口，协议自动降级为全量状态投影拉取，保障客户端与后端状态严格一致。

## 5. 核心设计原则与工程约束

系统的每一次演进与功能迭代均需恪守以下五项基本原则：

1. **本地优先与数据主权（Local-First & Data Sovereignty）**  
   用户的业务上下文、代码库、对话历史与私有模型凭据必须完整保留在本地工作区。禁止未经用户显式声明的外部云端遥测或状态回传。
2. **契约闭环先于编排协同（Contract Verification Before Orchestration）**  
   任何 Agent 或工具在加入多 Agent 团队编排前，必须先在单 Agent 模式下通过独立的输入输出契约测试与沙箱能力验证。未通过本地环境静态探测的能力，严禁标记为可运行状态。
3. **失败快速暴露与确定性回放（Fail-Fast & Deterministic Replay）**  
   底层异常与工具失败必须以明确的错误类型和上下文参数向上暴露，严禁静默吞食异常或做出不可靠的隐式猜测。系统状态必须能够从事件流实现 100% 确定性重放。
4. **最小特权与凭据零可见（Least Privilege & Zero-Visibility Secrets）**  
   工具调用与 MCP 执行仅授予当前任务所需的最小文件与网络权限。敏感凭据在流经协议层与前端渲染层时实现物理脱敏，彻底切断明文泄漏链路。
5. **不可变快照与环境确定性（Immutable Snapshots & Hermetic Environments）**  
   市场资产与依赖包采用 SHA-256 内容摘要进行版本锚定。执行态强锁定快照目录，杜绝因外部源或本地库动态更新导致的不可预测行为。系统升级遵循标准化数据平迁流程，详见 [升级与迁移指引](/zh-CN/docs/upgrade)。
